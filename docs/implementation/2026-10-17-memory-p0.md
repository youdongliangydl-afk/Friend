## 2. schema v4 与迁移

- 常量：`MEMORY_SCHEMA_VERSION=4`、`MEMORY_WRITER_VERSION=5`、`MEMORY_SCHEMA_TABLES`（18 张表）、`MEMORY_RECORD_COLUMNS`（17 列）、`MEMORY_RECORD_INDEX_DDL`。
- 新列：`kind_v2, subject_key, subject_cardinality, trust, authority, auto_published, policy_id, policy_version, score, conflict_state, lineage_root, semantic_digest, last_used_at, use_count, feedback_score, expires_at, deleted_at`。记录 json 仍是权威内容，列只是可查询投影；`records()/get()` 继续读 json，`write()` 24 列同步。
- 新表：`memory_subjects`、`memory_conflicts`、`memory_conflict_sides`、`memory_policies`、`memory_autopublish_audit`、`memory_reviews`（P1 预留）。索引：subject 活跃查询、kind/status、last_used、以及部分唯一索引
  `memory_records_single_subject (project_id, scope, subject_key) WHERE status='active' AND subject_cardinality='single' AND subject_key IS NOT NULL AND auto_published=1`。
- 迁移：v4 行不存在时，先 `VACUUM INTO memory-migration-backups/before-v4-<uuid>.sqlite`（目录 0700，失败即中止），单个 `BEGIN IMMEDIATE` 事务内建表/加列/回填/写安装画像/写 `memory_migrations(4)`；任何异常回滚且不写 v4 行。重复打开幂等（`migrated:false`，不新增备份）。并发首开在事务内二次检查，避免两个进程同时写 v4 行。
- 回填：`kind_v2`（method→NULL）、ASCII subject 的 `subject_key` + 注册表行、`trust`（user_explicit / source_verified / tool_verified / model_supported / model_inferred）、`authority`、`semantic_digest`（与 `memorySemanticDigest` 完全一致）、`lineage_root`；不编造 subject；同 subject 多 active 只保留一个 keeper（user 确认优先、updatedAt 最新），其余转 candidate + `conflictState='open'` + 迁移冲突对象（`opened_by='migration'`，确定性 id）。
- 围栏：Memory 表与 `documents(memory)` 的 writer 围栏升到 5；旧包（core 函数返回 4）写入报 `requires a newer writer`，读取仍可用；`recoverLearningJobs`/`cleanPrivacyBackups` 的裸连接同步使用 writer 5。`packages/core` 的 `RecordStore.friend_pi_writer_version` 返回 5，`requireSchemaWriter` 上界放到 5。
- 安装画像：`documents(memory, install-profile)={v:1,profile:'fresh'|'upgraded',at}`，首开后永不覆盖。首次打开时必须在 v2/v3 迁移写行之前判定，否则新装会被误判为升级（P0-I 修复）。

## 3. subject 与冲突

- 规范化：NFKC → trim → 小写 → 空白/下划线/连字符/冒号→`.` → 仅保留 `[a-z0-9._-]`；>200、空、`..` → undefined。**P0 仅 ASCII subject 成为可靠 key**；中文自由 subject 保持原 `subject` 字段并走 P0 前的标题/指纹冲突路径，避免 ASCII 折叠造成不同主题碰撞（`CedarArchive 服务端口`、`CedarArchive 部署端口` 都折叠成 `cedararchive` 的问题）。
- 注册表：`memory_subjects(project_id,scope,key)`，label/aliases/cardinality/value_type/sensitivity；save/迁移注册，已有 label/createdAt 保留、aliases 并集、cardinality 可被显式改 multi。
- 冲突生命周期：`open → resolved(keep_left|keep_right|merge|both|neither)` / `deferred → resolved`；`ConflictStore` 以列为主、json 保存完整对象，`transition` 用 `UPDATE ... WHERE status IN ('open','deferred')` 做 CAS。
- 检测：`detectSubjectConflict`：同 scope 同 subject 的 active peers 中 claimHash 相同→合并证据；有更正证据或 user_explicit+更正文案→替代；否则开冲突。新值一律 candidate，旧值保持 active 且可召回（蓝图 §6.3 的行为变更）。
- 裁决动作（controller）：`keep_*` 赢家 active/输家 inactive；`merge` 需用户正文，创建 active 合并记录（parentIds 两侧、证据/来源并集、父记录 inactive）；`both` 要求两侧条件非空且可区分，subject 注册表与记录列切 `multi` 后双 active；`neither` 双 inactive；`defer` 只迁移冲突状态。所有裁决在 dispatch 的 operationId 事务内执行，事件提交后发。
- 唯一性：部分唯一索引只约束**自动发布**记录；显式用户写入保持既有用户权威语义（P0 有意豁免，P1 冲突中心统一）。`accept`/`toggle` 遇到不同值的同 subject active peer 不再静默激活：开冲突并保持候选/停用；用户 `update` 视为明确更正，先退休不同值 peer 再激活。

## 4. 自动发布

- 模式：`off`（全候选）/`conservative`（90，仅 user_explicit/user_confirmed）/`standard`（70，user/source/tool verified，model_supported 的 fact/experience 过门禁）/`aggressive`（55，additional 独立观察的 profile/preference、≥2 项目 knowledge）。新装 `standard`，升级装 `conservative`。
- 10 门禁固定 ID：authority / quote / subject / safety / type / confidence / novelty / user-policy / cross-project / runtime。安全门禁失败标记 rejected；其余失败只降级为 candidate，并把确定性原因追加到原有 candidate reason（不覆盖旧诊断）。
- 评分 100：authority 0–40、quote 0–20、subject 0–20、independence 0–10、novelty 0–10；模型自评不参与。
- `CandidateFacts` 由 publish 阶段现有校验派生（不改安全语义）：trust 由 confirmedBy/来源角色/artifact 证据/authoritative 决定；quote verbatim/unique/conditions 沿用 upstream 校验；independentSources 取 factId/preciseKey 去重；P0 `independentProjects=1`（SourceRef 无 projectId，knowledge 的跨项目门禁要等 P1 源元数据）；secret 用 `[REDACTED_SECRET]` 判定；PII/提示注入用确定性正则；runtime 由 `ensure()` 保证。
- 审计 `memory_autopublish_audit`：publish/candidate/downgrade/revoke 行，含 score/gates/trust/authority/policy_id/policy_version/job_id/batch_key/rollback_token（仅 publish）/before/after(JSON，candidate reason 放 `after.reason`)。`batchKey=job.id` 支持按 job 批量撤销。
- API/事件：读 `conflict.list`、`autoPublish.status`（snapshot/list 也带 `conflicts`、`autoPublish`）；用户写 `conflict.resolve`、`autoPublish.settings`、`autoPublish.revoke`；事件 `memory.conflict.opened/resolved`、`memory.autopublish`（publish/settings/downgrade）、`memory.autopublish.revoked`。全部走同一 controller、operationId 幂等、expectedRevision/expectedStatus CAS，提交后才发事件。
- 撤销：按 ids/batchKey/policyVersion/since 找到未撤销 publish 行；记录 revision 未变才回滚（变化则 skipped），置 inactive/autoPublished=false、`suppress(reason='auto-revoked')`（含 M03 族）并失效子记录；重复撤销幂等；每次批次调用一次 `noteRevoke`（7 天滚动计数，5 次 correction+revoke 自动降一档）。
- 降级：`update` 用户更正 auto-published 记录时 `noteCorrection`；降级写 audit 行并发 `memory.autopublish {action:'downgrade'}`。

## 6. 行为变更（需要知道）

1. subject 冲突不再“双方一起从召回排除”：旧值保持 active/可召回，新值 candidate + `conflictId/conflictState='open'`，冲突对象一等化（蓝图 §6.3）。`capabilities.test.ts` 中 3 个用例按新语义更新断言（其余断言保留）。
2. `optimization.test.ts` 的 CedarArchive 用例保持通过：中文 subject 不走新 subject 模型，仍由 legacy 标题/指纹路径与用户更正机制处理。
3. 显式用户写入不受 auto-published 唯一索引约束（P0 取舍）；自动发布值必须遵守“同 subject 单 active”。
4. 无 subject 的有依据事实/经验仍可自动 active（gate 3 放宽），保持 P0 前 25 条抽取、artifact experience 等语义。
5. `conflict.list`/`autoPublish.status` 已加入 core 的只读动作集合，读操作不再触发 `memory.changed` 刷新事件；模型工具仍只能调用只读动作（写动作 origin 校验不变）。

## 9. 风险与边界

- 自动发布误发布的风险由门禁 + 审计 + 批量撤销 + 自动降级控制，P0 只做了确定性门禁；precision ≥95% 需要 P4 抽样/真实模型验证。
- 显式用户写入豁免唯一性：同 subject 多 active 仍可能出现（用户手动写入）；这是 P0 已知边界，P1 冲突中心统一。
- PII/提示注入门禁是确定性正则，不是完整安全模型；secret 依赖 `redactMemorySecrets` 的既有覆盖。
- `correction` 不写抑制族、`independentProjects=1`、`改用` 未进确定性 marker 均为记录在案的 P0 取舍。
