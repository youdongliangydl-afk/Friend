# @friend-pi/memory

Source-backed project experience and stable personal preferences for Pi. Node 24 is required. Pi JSONL owns native session history; Memory SQLite owns records, immutable revisions, suppression, operations and learning checkpoints. The plugin works without Expert or Swarm and does not invoke either capability during learning.

```sh
mkdir -p /absolute/path/plugins/memory
tar -xzf /absolute/path/friend-pi-memory-VERSION-HASH.tgz -C /absolute/path/plugins/memory
pi install /absolute/path/plugins/memory/package
```

Pi host packages are peers. UI, `friend_memory` and `/memory ACTION JSON` call the same controller. No embedding model, reranker, vector service, duplicated chat store or fork of the Pi loop is added.

## Records and writes

New records are `fact`, `experience` or `preference`; preferences use personal scope. Records carry aliases, complete conditions, evidence, explicit dependencies, validity/review times, revisions and content SHA-256. Legacy `method` records retain IDs and history for read-only inspection and are excluded from recall. Old distill checkpoints migrate to cancelled; Memory no longer creates or submits Expert methods.

`feedback`, `save`, `update`, `accept`, `toggle`, `forget` and learning controls accept `operationId`. Retries with the same ID and payload return the committed result; reuse with another payload fails with `VERSION_CONFLICT`. Existing mutations accept `expectedRevision` (the legacy `revision` spelling remains supported). `update` accepts a patch. Origin comes from the trusted entry point; model arguments cannot elevate it. Legacy calls without operation IDs remain compatible but cannot reconcile a timeout by identity.

Explicit user remembrance is active; model proposals remain candidates until deterministic validation. Automatic stable preferences require an explicit long-term user statement or explicit remembrance confirmation. Repeated observations, independent native entries and trusted sources alone do not create a long-term instruction. Forked copies add no independent support. Attachments, quoted instructions, temporary goals and assistant self-evaluation cannot become user authority.

Sources use exact native UTF-16 spans/hashes and artifact observations use registered version/hash/ranges, receipt ID and observer. Unknown or unobserved ranges fail closed. SourcePolicy checks public policy and frozen dependencies on the same SQLite connection as the short business transaction. Personal cross-project source grants expose only registered spans, never the whole originating project.

## Retrieval and evidence

- `search {query?,scope?,limit?,match?,taskContext?}` returns effective records. Weighted FTS5 BM25 uses title 5, aliases 3, body 1; NFKC/Latin normalization and CJK bigrams affect only the index. Exact IDs, titles, error codes, entity names and code/path literals are prioritized. The bounded long-query term set protects path/code terms, then rare indexed terms before unknown filler; CJK bigrams and BM25 remain the only retrieval index. Existing default all-term matching is preserved; `match:"adaptive"` tries conjunction then bounded disjunction, and `match:"any"` is explicit disjunction.
- `search.explain {queryId}` or `{query}` reports matched fields/terms, filtering reasons and rule version. Query caches expire after 24 hours and retain terms, not full prompts.
- `directory {query?,scope?,budget?}` returns versioned pointers and explicit omissions. `select {query?,scope?,budget?,limit?,taskContext?}` returns separate directory and whole-body selections. Defaults are 1500 directory characters, 3500 body characters and 6 records. At most two clearly applicable explicit long-term preferences precede other relevant records. Preferences with unclear applicability remain directory pointers. Body and complete conditions are admitted together; oversized bodies remain unread pointers with reasons and exact revision references rather than truncated claims. No query-rewrite model, vectors, cross-project history search or Topic/Rebuild dependency is added. The foreground agent may proactively search with 1–3 distinctive keywords, read complete bodies/conditions, and follow only registered valid permitted original-source references. A hit is not automatically authoritative; zero hits do not prove that history does not exist.
- `read {id,revision?,source?}`, `read.range {id,revision,cursor?,maxChars?}` and `source.read {source|artifact,cursor?,maxChars?}` provide immutable versions, bounded UTF-16 pages and controlled original source access. Pages report exact visible ranges, full length, slice hash and next cursor; a stale current revision fails CAS. The read limit is 8000 characters.
- `usage` distinguishes prepared/selected, context injection, observed provider request, response and native tool reads. Directory and body each have EvidenceReceipts. No receipt claims causal model adoption or answer correctness. `source.read` records actual tool observation separately. Native receipts are journaled before SQLite projections and restore on cold start.

Source-only updates compare normalized source identity sets (ignoring order and display labels). A changed source advances the durable invalidation epoch, invalidates the prior Memory revision and its descendants, and emits `sources-changed` with record IDs and no retired native sources. Still-valid original text remains queryable through independently supported records; the updated record can use its new sources. Equivalent source sets do not invalidate descendants.

Expired records are excluded; `reviewAfter` only marks review due. Conflicting subject records are excluded from automatic use. New user corrections, forgetting and source withdrawal take precedence over late learning results. Forget removes body/version/index/evidence data and redacts body/title/conditions from usage and operation projections, retaining tombstones and scoped suppression. Native historical receipts remain immutable; original-history deletion is a host operation. A new explicit user remembrance can lift only its matching scoped suppression.

## Task context and user feedback

`taskContext:{goal?,scenario?,entities?:string[]}` uses current task facts directly. Local CJK/BM25 terms augment candidates and order results within the explicit query's exact ID/title/alias/code/path tier. Normalization applies NFKC, Latin lowercasing and whitespace folding, and sorts/deduplicates entity names. No model request or embedding is used. If query is omitted, nonempty task context supplies the local query. Context never widens project/source permissions.

Trusted user entry points may call `feedback {id,revision,kind:"relevant"|"irrelevant"|"outdated",taskContext?,operationId?}`. The current effective record and exact revision are required. Feedback uses the existing transactional operation ledger; identical retries return the committed result and changed payloads conflict. Result fields are `{id,revision,kind,projectId,contextKey,taskContext?,reviewQueued,at,operationId}`; `snapshot.feedback` exposes current-revision feedback. Ranking changes apply only to the same normalized task context in the submitting project; feedback without a task context is recorded but has no ranking effect. Personal records do not carry feedback across projects. `outdated` sets `reviewQueued:true` for user review, without editing content, validity, conditions, preference records or learning inputs. Later correction revisions invalidate old ranking signals. Forget removes stored feedback and its contextual operation payload.

Every full selected record carries complete `conditions:[]`, `validFrom:null|string`, `validTo:null|string`, original source refs, `id`, `revision`, `hash = digest(content)` and `semanticDigest = digest({id,revision,content,conditions,validFrom,validTo,scope})` with that exact property order. All conditions participate, including those beyond display previews. Selected records are deeply frozen snapshots. Directory entries omit the body but preserve semantic metadata and sources. A `read.range` page preserves the full record hash/semantic digest and adds `sentSliceHash` for only the returned page; consumers must not digest the partial body as a complete record.

## Independent background learning

The persistent pipeline is `extract → validate → publish → optional compact`. Ordinary batches use one extraction call; validation and publication call no model. Compaction is limited to at least three active same-subject records, at most one extra call, and must retain the original claims, conditions and evidence. It never creates Expert methods.

Batches cover at most 80 native entries and 48000 UTF-16 source characters; oversized entries are split with exact ranges. Complete and pending ranges are tracked separately. Every redacted original proposal has a stable identity bound to job, extract operation, original ordinal and hash, plus status, rejection reason, memory ID and correction targets. Ordinary rounds target 12 proposals; connected correction groups are never split, and a larger group occupies its own round. Restart resumes saved unprocessed proposals without another extraction. Invalid fields or fabricated quotes isolate their proposal/group; independent valid proposals continue. A replacement becomes active, old facts and descendants become inactive/invalidated, and proposal progress commits in one transaction only after publication authority/source checks. Bad replacements cannot retire valid facts. The same job retains its cumulative default six-call budget. Exhaustion prevents new model calls while deterministic validation/publication continues; optional compact failures or insufficient budget do not block published results. Unknown remote results, source/permission withdrawal and lost leases stop the related job without erasing committed progress. The source/model/rule fingerprint prevents rescanning covered ranges. Jobs freeze the explicitly configured background model or source task model and register an independent LearningBudget; the foreground run is provenance, not reusable quota.

The desktop host and native extension use `peekLearningJob` and `executeLearningJob(id,ctx,{signal?,lease?,budgetId?})`. Generic host admission honors foreground priority; normal foreground input does not abort in-flight work. Pausing, source invalidation, stale owner token or public policy change prevents late publication. Claims have a 60-second lease with 10-second heartbeats. Ordinary failures stop after three attempts; authentication/configuration waits without retry churn. Unknown remote results persist as `operation_unknown` and cannot be blindly retried. `learning.status` and `diagnostics` distinguish source entry into extraction, processed proposals, published records, candidates/rejections, pending continuation, and cumulative budget. `learning.run/retry/pause/resume/settings` and `operation.get` expose the same durable state.

## Read-only impact previews

`impact.preview {action:"update"|"forget",id,patch?}` is user-only and returns affected record revisions and complete-record digests, native/artifact source validity, dependency validity, public source/policy epochs, candidate digest and `previewToken`. The preview uses a coherent read-only SQLite snapshot and does not create SourcePolicy fences. Related source/artifact/dependency validity states and the global permission-policy epoch expire the preview even if the Memory revision did not change. The general source epoch is diagnostic only: unrelated background publication does not force another preview. It changes no records, learning state or watermarks. Submit the unchanged patch/token to the existing `update` or `forget` controller; changed records, descendants, source state or candidate content reject with `VERSION_CONFLICT` and require a fresh preview. Existing revision-CAS clients remain compatible. Diagnostics and receipts distinguish selection, actual context/request visibility, and objective correctness; visibility is not model adoption or correctness.

## Managed Markdown and migration

`memory-views/<scope>/MEMORY.md`, `records/<id>.md` and `manifest.json` are read-only derived views in application data, not files in the user repository. SQLite changes enqueue a durable projection. Files are staged, bodies atomically installed and the manifest replaced last; revision/epoch/hash or external-edit drift triggers regeneration, never import. Model reads use the controller so ordinary filesystem reads cannot silently adopt stale projections. `projection.status/rebuild` validates/reconciles views. A failed projection does not roll back valid database content.

Schema v2 and durable-proposal migration v3 each back up SQLite, record a checksum and apply changes transactionally. Writer version 4 fences upgraded Memory tables and documents against older clients; disabling the feature does not downgrade the database. Forgotten record bodies are also removed from proposal payloads and managed migration backups. Unavailable legacy evidence remains a candidate; native JSONL is not rewritten. `export` remains a user copy and is independent of managed views.

Focused tests cover controller safety and public Pi faux requests. Real-model semantic quality and packaged Computer Use journeys require integration acceptance and are not implied by these tests.

## P0 foundation: schema v4, subjects/conflicts, auto-publish (2026-10-17)

Memory now persists schema v4 (`MEMORY_SCHEMA_VERSION=4`) behind writer version 5. The first open upgrades a v3 database with a checksum-guarded `VACUUM INTO` backup inside `memory-migration-backups/` (private directory), one `BEGIN IMMEDIATE` transaction, an install profile (`fresh` vs `upgraded`), and a v3→v4 backfill of `kind_v2`, `subject_key`, `trust`, `authority`, `semantic_digest`, `lineage_root` plus a one-time isolation of same-subject active duplicates into candidates with conflict objects. Older writers fail closed on every upgraded table/document while reads still work; disabling Memory does not downgrade the database. Fresh installs get `standard` auto-publish; upgraded installs default to `conservative` (observed rollout). Migration is idempotent, backs up first, and never fabricates a subject key.

**Subject keys and conflicts.** Model-proposed subjects are normalized into dotted lowercase keys; only ASCII subject strings become reliable keys (legacy Chinese free-form subjects keep the pre-P0 title/fingerprint conflict path). A per-project subject registry stores label, aliases, cardinality, value type and sensitivity. For auto-published records with a single-cardinality subject, at most one value is active (`memory_records_single_subject` partial unique index predicated on `auto_published=1`). Direct explicit user writes remain user-authoritative and are exempt in P0; P1's conflict center will unify them. A differing automatic value never silently replaces the current one: the old record stays `active` and usable, the new value stays `candidate` with `conflictId`/`conflictState:"open"`, and a first-class conflict object is opened with `left`/`right` sides. `conflict.list` and `conflict.resolve {id,resolution:"keep_left"|"keep_right"|"merge"|"both"|"neither"|"defer",content?,notes?,expectedStatus?}` (user-only, operation-id idempotent, CAS on conflict status) rule: keep moves one side active and retires the other, `merge` requires user content and creates one active record from both, `both` requires distinguishable non-empty conditions and switches the subject to multi cardinality, `neither` retires both, `defer` keeps the object open. `memory.conflict.opened`/`memory.conflict.resolved` are emitted after commit.

**Auto-publish gates.** Learning publication still separates model proposal from deterministic authority (`authoritative` checks are unchanged). When authoritative, `CandidateFacts` (kind, trust, authority, verbatim/unique quote, complete conditions, subject state, novelty, independent support, safety flags, user policy, daily quota, runtime health) are evaluated by `decideAutoPublish`: four modes (`off`, `conservative` 90, `standard` 70, `aggressive` 55), ten fixed gates (`authority`, `quote`, `subject`, `safety`, `type`, `confidence`, `novelty`, `user-policy`, `cross-project`, `runtime`) and the blueprint 100-point score. Safety gate failures are recorded as rejected; other failures append the deterministic reason to the existing candidate reason so prior candidate diagnostics stay stable. Each eligible decision writes `memory_autopublish_audit` with score/gates/trust/authority/policy version/`batchKey=jobId`; active rows carry a `rollbackToken`. `autoPublish.status`, `autoPublish.settings` (user CAS patch of mode/minScore/maxAutoPerDay/requireReview) and `autoPublish.revoke` (user rollback by record ids, batchKey, policyVersion or since) are exposed through the same controller; revoked records become inactive, are suppressed with reason `auto-revoked`, stay out of automatic revival, and repeated user corrections/revocations count toward a 7-day automatic downgrade (`aggressive→standard→conservative`) emitted as `memory.autopublish {action:"downgrade"}`. `snapshot` and `list` expose `conflicts` and `autoPublish`.

**Cross-plugin hardening.** M01: user intent rules (`记住/记一下/记下来/remember`, polite prefixes, negation guard, correction/preference/quoted cues) live in `language.ts` as a versioned rule table instead of scattered inline regexes. M02: both desktop workers use the versioned foreground-lease contract (`apps/desktop/src/foreground-lease.ts`, v2 payload with kind/session/heartbeat/expiry, v1 read compatibility), so a dead or expired foreground lease no longer blocks the learning host. M03: forgotten and auto-revoked values record a deterministic content-bytes suppression family; automatic proposals whose wording/quote is a paraphrase, sub-quote or bounded extension of that family are refused before becoming candidates, while explicit user re-statements remain possible. Correction statements are exempt from family suppression because they necessarily re-quote the retired value; correction authority is re-validated at publish instead.

**Behavior change from the blueprint.** The three subject-conflict cases in `capabilities.test.ts` previously asserted both sides were excluded from recall; per blueprint §6.3 the current value now stays usable and only the new value is isolated. Those assertions were updated with the new conflict-object expectations. Subjectless publication keeps the pre-P0 behavior (the relaxed gate 3 permits sourced subjectless facts) so existing experience/fact publication and 25-record extraction semantics are unchanged. `改用`/`改一下配置。` deterministic settlement markers remain a documented follow-up (covered through explicit `factId` corrections today).

Focused coverage: `packages/memory/test/*.test.ts` now runs 246 tests — the original 135 plus v4 migration, subject/conflict data layer and controller flows, auto-publish gates/scoring/audit/rollback/downgrade, P0 acceptance, language rules and suppression families. Desktop-level confirmation still requires the packaged Computer Use journeys and real-model semantic quality described in the blueprint P4 gates.
